# GAME_PLAN — «Остров чудиков» для CRM iCubeRobots

Статус: **правила (раздел 13) и технические решения Т1–Т10 (раздел 15) утверждены 02.11.2026. Ничего не реализовано, код, базы и сервер не менялись.**

Игра — для детей клуба iCubeRobots: звёзды за реальные посещения (в игре это отдельная валюта; монеты зарабатываются внутри игры), свой остров, постройки, визиты к друзьям и лайки. Интеграция только с этой CRM; мультиарендность и «платформа» вне рамок.

## 1. Что в коде CRM определяет решения

Проверено по `main` (коммит от 2026-10-21):

| Факт в коде | Следствие для игры |
| --- | --- |
| В `roles` есть `child`, есть таблица `child_user_accounts (child_id ↔ user_id)` | Учётные записи детей уже предусмотрены схемой — **миграция CRM для них не нужна**. |
| `authService.login` и `authenticateToken` пускают только `director/teacher/partner/parent` | Сейчас ребёнок **в принципе не может получить сессию CRM**. Это ценная защита, её сохраняем. |
| Часть маршрутов CRM требует только факта входа (`/push/*`, `/notification-settings`, `/releases/current`, `/auth/me`), а у роли `child` уже есть право `own-attendance:read`, которое открывает `/parent/children/:id/attendance` | Если пустить ребёнка в сессию CRM, ему станут доступны маршруты, не рассчитанные на детей. **Сессия CRM ребёнку не выдаётся вообще.** |
| Cookie `icube_session` с `path=/api/v1`, `SameSite=Lax`, `httpOnly`, `Secure`; отдельных CSRF-токенов нет | Cookie CRM не трогаем. У игры своя cookie и свои правила CSRF. |
| Ограничитель попыток входа — в памяти процесса (`login-rate-limit.mjs`) | Попытки детского входа ограничивает **CRM** во внутреннем API `verify-child`: тем же модулем, отдельным экземпляром со своим счётчиком. Игра этот модуль не импортирует: он через `catalog.mjs` зависит от `db.mjs`. |
| `npm run migrate` читает только `database/migrations/` и проверяет имя базы по `APP_ENV` | Миграции игры в отдельной папке со своей командой никогда не запустятся миграцией CRM. |
| Посещение: `attendances.present`, занятие `lessons.status IN (scheduled,in_progress,completed,cancelled)`; исправления делаются через reversal-записи | Монеты считаются от состояния посещений, а не от событий: так исправления обрабатываются автоматически. |
| **(этап 0)** Строки `attendances` в CRM удаляются физически: при удалении занятия, сбросе занятия, удалении ребёнка из доп. состава, удалении ученика | Сверка «что изменилось с момента X» удаления не увидит. Сверяем **полный список** засчитанных посещений каждого ребёнка (раздел 5). |
| **(этап 0)** Вход и проверка сессии CRM пропускают пользователя, если у него есть **хотя бы одна** взрослая роль (`roles.some(...)`) | Детская учётка — **всегда отдельный пользователь ровно с одной ролью `child`**. Проверка ребёнка отклоняет пользователя с любой другой ролью. |
| **(этап 0)** Ребёнка можно удалить из CRM целиком (`catalog.mjs`, жёсткое удаление с `child_user_accounts`) | Вход закрывается, данные игры сохраняются (Т6). |

## 2. Архитектура

```
Браузер ребёнка
  └─ https://<test-домен>/game/          → статика игры (Nginx)
  └─ https://<test-домен>/game/api/*     → игровой процесс 127.0.0.1:3100
                                              │  своя сессия icube_game_session
                                              │  своя база icube_game_test
                                              ▼
                                    внутренний API CRM 127.0.0.1:3001
                                    (не проксируется наружу, секретный заголовок)
                                              ▼
                                    CRM-процесс → icube_test

Браузер сотрудника
  └─ https://<test-домен>/api/v1/*       → CRM 127.0.0.1:3000 (как сейчас)
```

**Репозиторий:** папка `game/` в `icube-crm`.

```
game/
  server/        игровой API (Express), сессии, звёзды, острова
  client/        страница игры
  migrations/    миграции только для icube_game_*
  tests/
```

**Принцип:** игра не имеет **никакого доступа к базе CRM**. Всё, что ей нужно от CRM, она получает через узкий внутренний API, который CRM сама контролирует.

## 3. Авторизация ребёнка

### Сравнение вариантов

| | A. Общий модуль авторизации | B. Внутренний API CRM (**выбран**) |
| --- | --- | --- |
| Как работает | Игра импортирует код CRM и сама читает `users`, `auth_sessions` | Игра передаёт логин/пароль во внутренний API CRM; CRM проверяет и отвечает «это ребёнок N» |
| Права игры на базу CRM | Нужно `SELECT` на `users.password_hash`, а для создания сессий — запись в `auth_sessions` | **Никаких** |
| Зависимость от внутренностей CRM | Схема таблиц, формат токенов, логика ролей | Только контракт из 3–4 методов, покрытый тестами |
| Если в игре уязвимость | Злоумышленник читает хэши паролей всех пользователей CRM | Доступны только данные, которые CRM отдаёт игре |
| Цена | Меньше кода | Чуть больше кода в CRM |

**Почему B:** хэши паролей директора, преподавателей и родителей не должны быть доступны процессу, который мы будем активно и быстро менять. Цена B — несколько небольших методов в CRM.

### Как работает вход

1. Ребёнок открывает `/game/`, вводит логин и пароль.
2. `POST /game/api/login` → игровой процесс → `POST 127.0.0.1:3001/internal/game/verify-child` (логин, пароль, IP ребёнка: для CRM адрес запроса всегда `127.0.0.1`, а счётчик попыток считает пару IP + логин).
3. CRM проверяет пароль своим кодом (bcrypt), что пользователь `active`, что у него **только** роль `child` (никаких других) и связь в `child_user_accounts`, что ребёнок в статусе `active` или `paused` (Т6). Ограничение попыток входа выполняется здесь же, на стороне CRM; тот же ответ «неверный логин или пароль» для всех отказов. Возвращает `{ childId, userId, displayName, tokenVersion }`. Сессию CRM не создаёт.
4. Игра создаёт свою сессию в `icube_game_test.game_sessions` (хранится только хэш токена) и ставит cookie `icube_game_session`.
5. При запросах игра сверяет `tokenVersion` и статус ребёнка у CRM не чаще раза в минуту на сессию. Директор сбросил пароль или заблокировал доступ → сессии игры гаснут.

### Логин ребёнка

- Директор в карточке ребёнка нажимает «Доступ в игру»: создать / сбросить пароль / отключить. По аналогии с доступом преподавателя (`createTeacherAccess` / `resetTeacherPassword` / `disableTeacherAccess`).
- Ребёнок вводит короткий логин, например `misha.k`. В `users.email` он хранится как `misha.k@child.icube.local`: схема CRM не меняется, уникальность обеспечивает существующий ключ. Обычный вход CRM такого пользователя всё равно не пустит, потому что роль `child` там запрещена.
- Пароль ребёнка — по общим правилам CRM (не короче 8 символов). Для 6–10 лет можно генерировать запоминающийся, например `кот-7-луна`, и печатать карточку для родителя.

### Что ребёнку недоступно (проверяется тестами)

- Любой маршрут `/api/v1/*` CRM: сессии CRM у ребёнка нет, `authenticateToken` роль `child` не пропускает. Тест: логин ребёнка через `/api/v1/auth/login` → отказ; игровой токен в cookie `icube_session` → 401.
- Дополнительная страховка на этапе 2: у роли `child` в `auth.mjs` убираются права `own-profile:read` и `own-attendance:read` (сейчас второе совпадает с маршрутом родителя `/parent/children/:id/attendance`). Роль `child` в CRM — с пустым набором прав.
- Создание детской учётки никогда не добавляет пользователю другие роли; к существующему взрослому пользователю роль `child` не добавляется (тест).
- Внутренний API `:3001`: снаружи недоступен, и без секрета отвечает 404.
- Чужие острова только на чтение (постройки, лайки); изменять можно только свой.

## 4. Маршруты, cookie, CSRF

| Путь | Куда | Доступ |
| --- | --- | --- |
| `/game/` | статика Nginx | все |
| `/game/api/*` | `127.0.0.1:3100` | сессия игры |
| `/api/v1/*` | CRM `127.0.0.1:3000` | **без изменений** |
| `127.0.0.1:3001/internal/game/*` | CRM, отдельный порт | только игровой процесс, секрет `GAME_INTERNAL_TOKEN` |

- Cookie CRM (`icube_session`, `path=/api/v1`) **не меняется**.
- Cookie игры `icube_game_session`: `path=/game`, `httpOnly`, `Secure`, `SameSite=Strict`.
- CSRF: все изменяющие запросы игры принимают только `Content-Type: application/json` и проверяют заголовок `Origin` на совпадение с доменом. Вместе со `SameSite=Strict` этого достаточно без отдельных токенов.
- Внутренний API слушает **отдельный порт** `3001`, а не путь внутри `:3000`. Даже если Nginx на сервере проксирует в CRM не только `/api/v1`, внутренние методы снаружи недоступны. Порт открывается, только если в `.env` CRM заданы `GAME_ENABLED=true` и `GAME_INTERNAL_TOKEN`.
- В игровом процессе нет служебных маршрутов наружу. Админ-операции (бонусы, сверка) — команды `npm run game:*` на сервере или методы под ролью директора, решим на этапе 6.

### Внутренний API CRM (полный контракт)

| Метод | Назначение |
| --- | --- |
| `POST /internal/game/verify-child` | логин+пароль+IP ребёнка → ребёнок или отказ; здесь же ограничение попыток входа |
| `GET /internal/game/children/:childId/status` | активен ли, текущий `tokenVersion`, имя |
| `GET /internal/game/children/:childId/qualifying-attendance` | **полный** список засчитанных посещений ребёнка по правилам раздела 13: `attendanceId, lessonId, startsAt, attendanceType, isTrial` |
| `GET /internal/game/children?ids=` | статусы пачки детей для фоновой сверки (существует / `active` / `paused` / закрыт) |

Только чтение (кроме проверки пароля). Никаких денег, телефонов, родителей, оплат.

Обратный канал (решение Т4): игровой процесс слушает `127.0.0.1:3101/internal/*` с тем же секретом; CRM вызывает `POST /internal/bonuses` и `POST /internal/bonuses/:id/revoke` только после своей проверки прав и границ доступа. Наружу не проксируется.

## 5. Звёзды (валюта за занятия)

### Что уже есть в игре (проверено в коде «Island of Oddballs», 02.11.2026)

В игре **две валюты** (`src/logic/economy.js`, `CLAUDE.md` игры):

| Валюта | Откуда | Связь с CRM |
| --- | --- | --- |
| **Монеты** | внутри игры: доход чудиков в копилку, тропа, задачка дня, уровни, коды занятий | **нет** — остаются игровой механикой |
| **Звёзды** | **только** за занятия и бонусы преподавателя | **да** — это и есть «валюта за посещения» |

- За занятие: `CONFIG.rewards.lessonStars = 3` **звезды**.
- Бонус преподавателя: `CONFIG.rewards.teacherBonusStars = 1` звезда (в игре — фиксированный).
- Звёзды не сразу на балансе: они кладутся в **сундук церемонии** (`ceremony.pendingStars`) и зачисляются, когда ребёнок откроет сундук при входе.
- Цены в звёздах: фонтан 2, солнечная панель 2, мастерская 3, эволюция/особое скрещивание 5, редкое яйцо 6. То есть 1 занятие ≈ одна постройка за звёзды, 2 занятия ≈ редкое яйцо.
- Покупка требует, чтобы звёзд хватало (`canAfford`) — в долг уже нельзя.

**Решение:** то, что в правилах владельца названо «монетами за занятие», в игре — **звёзды**. Значение берём из игры: **3 звезды за занятие**, настройка `lessonStars`, а не новое число. Журнал и сверка ниже — для звёзд. Монеты остаются внутриигровой валютой и с CRM не связаны.

### Журнал звёзд

Таблица `game_star_entries` (только добавление, без UPDATE/DELETE):

| Поле | Смысл |
| --- | --- |
| `child_id` | ребёнок из CRM (не `user_id`: доступ можно пересоздать, игра продолжится) |
| `kind` | `attendance`, `attendance_reversal`, `trial_followup_bonus`, `trial_followup_reversal`, `staff_bonus`, `staff_bonus_revoke`, `purchase` |
| `amount` | ± звёзды |
| `attendance_id` / `bonus_id` | к чему относится запись |
| `idempotency_key` | уникальный |
| `created_at` | |

**Внутренний баланс** = сумма `amount`, может быть отрицательным. Начисления сначала попадают в сундук церемонии: «в сундуке» = начисления, ещё не открытые ребёнком; открытие сундука переносит их на видимый баланс.

### Сверка посещений (по ребёнку целиком)

Игра берёт у CRM **полный** список засчитанных посещений ребёнка и сравнивает с журналом. Для каждого `attendance_id`, который есть в списке CRM или в журнале:

- **цель** = 3 звезды, если посещение засчитано (правила 2–4: присутствовал, занятие завершено и не удалено, не ознакомительное, занятие не раньше `earning_since`), иначе 0;
- **факт** = сумма записей журнала по этому `attendance_id`;
- цель ≠ факт → одна запись на разницу.

Так обрабатываются исправления и физическое удаление посещений/занятий в CRM: посещение пропало → цель 0 → `attendance_reversal`. Повторная сверка ничего не добавляет. Две сверки одновременно не пройдут: блокировка строки игрока в транзакции + уникальный `idempotency_key` (`att:<attendanceId>:<n>`).

**Бонус ×2 после ознакомительного** — отдельная запись `trial_followup_bonus +3` (вторая половина двойного начисления), привязанная к ребёнку, а не к занятию: уникальный ключ `trial_followup:<childId>`. Сверка каждый раз заново определяет, какое посещение — «первое обычное после ознакомительного» (правило 2, Т1, Т2). Если его исправили, бонус отзывается записью `trial_followup_reversal` и, если положено, переходит на следующее подходящее посещение. Сверка — раз в 10–15 минут и при входе ребёнка.

### Потраченные и отменённые звёзды

| Событие | Внутренний баланс | Ребёнок видит |
| --- | --- | --- |
| Посетил занятие, открыл сундук | 3 | 3 |
| Купил мастерскую (−3) | 0 | 0 |
| Посещение отменили (−3) | −3 | **0** |
| Следующее занятие (+3) | 0 | 0 |
| Ещё занятие (+3) | 3 | 3 |

Купленное не отбирается. Показывается `max(0, баланс)`. Покупка — только если внутренний баланс ≥ цены. Проверка и запись покупки — в одной транзакции.

### Бонусы сотрудников

- Выдают директор, партнёр, преподаватель, **количество вводит сотрудник**.
- Запись: кто выдал (`user_id` CRM), кому (`child_id`), сколько, когда, причина, ключ идемпотентности. Двойное нажатие → одна запись.
- Ошибочный бонус не удаляется, а **отзывается** (`staff_bonus_revoke`) с указанием, кто и почему. Отозвать может автор бонуса или директор.
- Права — **те же границы, что в CRM** (Т5): директор — все дети; партнёр — дети своего проекта; преподаватель — дети своих групп и занятий за 60 дней.
- Сумма — 1–10 звёзд за выдачу, подтверждение при сумме больше 3 (Т7).

## 6. Независимость релизов и миграций

- **На сервере две отдельные папки из одного репозитория:** CRM test (как сейчас) и `/opt/icube-game-test` для игры. Каждая обновляется своим `git pull`/checkout и перезапускает **только свой** systemd-юнит. Обновление CRM не трогает игру, и наоборот.
- Свой юнит `icube-game-test.service`, пользователь `icube-game` без доступа к папкам CRM и к `.env` CRM.
- **Миграции:** CRM — `npm run migrate` (только `database/migrations/`). Игра — `npm run game:migrate` (только `game/migrations/`). Раннер игры откажется работать, если имя базы не `icube_game_test` / `icube_game_prod` для соответствующего `APP_ENV`.
- **CI-проверки:**
  - в `database/migrations/` нет таблиц `game_*`;
  - в `game/migrations/` нет обращений к таблицам CRM;
  - раннер игры падает на имени `icube_test` / `icube_prod`;
  - код в `game/` не импортирует модули `backend/` и `database/` и не открывает соединений с базой CRM.
- **Флаг:** всё новое в CRM (внутренний порт, кнопка «Доступ в игру») работает только при `GAME_ENABLED=true`. На проде флага нет — код ничего не делает, даже если попадёт туда с обычным релизом.

## 7. Безопасность

- Production CRM, `icube_prod` и боевой домен в этом плане **не меняются**.
- Пользователь БД игры `icube_game_test_app` имеет права только на `icube_game_test`. Прав на `icube_test` и `icube_prod` у него нет.
- Claude Code **не получает** SSH-доступа к серверу и доступа к базам. Команды для сервера готовятся в репозитории, выполняет их владелец.
- Детям не даём свободный текст друг для друга: ник выбирается из готовых слов («Смелый Кот 7»), общение — только лайки. Для 6–10 лет это проще, чем модерация.
- Правила для Claude Code — в `CLAUDE.md` (раздел 10).

## 13. Утверждённые правила (02.11.2026)

1. **Валюта и количество.** За посещения начисляются **звёзды** (не монеты). Базовое начисление — **3 звезды** за засчитанное занятие (значение из игры, `CONFIG.rewards.lessonStars`). Монеты остаются внутриигровой валютой и с CRM не связаны.
2. **Ознакомительное занятие — 0 звёзд.** Первое обычное (не ознакомительное) занятие после ознакомительного — **6 звёзд** (3 базовых + 3 бонуса ×2) при условиях Т1–Т2. Бонус ×2 — **один раз на ребёнка за всё время**; ознакомительные в других направлениях его повторно не дают.
3. **Обычные посещения.** Звёзды за каждое фактически посещённое занятие, кроме ознакомительного, в любой группе и направлении. Засчитано = `attendances.present = TRUE`, занятие `completed`, не удалено, `is_trial = FALSE`. Занятие в чужой группе (`attendance_type = 'extra'`) засчитывается как обычное.
4. **Начало начислений** — с первого подходящего посещения после создания **первого** игрового доступа (Т3). Посещения до этого не учитываются.
5. **Бонусы.** Выдают директор, преподаватель и партнёр в пределах своих прав в CRM (Т5); сумму выбирает сотрудник в пределах защитного лимита (Т7); сохраняется кто/кому/сколько/когда/почему; защита от повторного начисления; ошибку исправляют отзывом с сохранением истории.
6. **Архив и пауза.** Ребёнок на **паузе** продолжает играть. Архивный, завершивший или удалённый из CRM — вход отключён, весь игровой прогресс сохраняется (Т6).
7. **Возвращение.** Директор или партнёр восстанавливает или создаёт доступ к тому же ребёнку. Звёзды, остров, покупки и **история начислений не обнуляются**; за старые занятия повторно ничего не начисляется (Т3).
8. **Детский доступ.** Логин и пароль создают директор и партнёр (партнёр — только детям своего проекта). Ребёнок входит сразу в игру, без детского кабинета.
9. **Серверная защита.** Звёзды, покупки за звёзды и проверка кодов занятий выполняются **только на сервере** (Т8, Т9).

## 15. Принятые технические решения (02.11.2026)

| # | Решение |
| --- | --- |
| **Т1** | ×2 получает только ребёнок, чьё **первое в истории CRM** обычное посещение произошло **после** `earning_since`, и ему предшествовало ознакомительное. Кто ходил на обычные занятия до запуска доступа, ×2 не получает. |
| **Т2** | Если ознакомительное было до создания доступа, а первое обычное — после, ×2 **даётся**: ознакомительное само по себе звёзд не приносит. |
| **Т3** | Игра записывает `earning_since` один раз — при **первом** создании доступа — и больше не сдвигает (пересоздание доступа после архива его не меняет). Граница — начало дня создания доступа по `Asia/Sakhalin`: занятие в день создания доступа засчитывается. Данные игры привязаны к `child_id`, а не к учётной записи. |
| **Т4** | Бонусы хранятся в **игровой базе**. Сотрудник выдаёт бонус в CRM → CRM проверяет право и границы доступа, пишет запись в существующий `audit_log` и передаёт бонус игре по внутреннему каналу `127.0.0.1:3101` с секретом. **Миграция CRM не нужна.** Если игровой процесс остановлен, CRM показывает «игра временно недоступна», бонус не теряется молча. Отзыв — тем же каналом. |
| **Т5** | «Мои дети» преподавателя = дети из состава групп, где он основной преподаватель, и дети из состава занятий, которые он фактически вёл за последние 60 дней. Партнёр — дети своего проекта (`assertOwned`). Директор — все. Новая проверка в CRM покрывается тестами (чужой ребёнок → 403). Отозвать бонус может его автор или директор. |
| **Т6** | Вход в игру разрешён при `children.status IN ('active','paused')` и `users.status = 'active'`. `lead`, `finished`, `archived`, удалён из CRM — вход закрыт, данные игры хранятся без срока. При возвращении прогресс продолжается. |
| **Т7** | Сумма бонуса — на выбор сотрудника, от 1 до **10** звёзд за одну выдачу (настройка `GAME_BONUS_MAX_STARS`); при сумме больше 3 CRM просит подтверждение. Повтор нажатия — одна запись (ключ идемпотентности). |
| **Т8** | Баланс звёзд, сундук, покупки за звёзды — **только на сервере**, клиент лишь показывает и отправляет намерение «купить X». Кнопки «занятие посещено», «бонус преподавателя», «+звёзды», «+монеты», промотка времени из меню разработчика **на сервере недоступны** (на test — только по отдельному флагу для отладки, на prod — никогда). Монеты и остальной прогресс тоже переезжают на сервер (визиты к друзьям, защита от подделки); объём переноса уточняется на этапе 5 без изменения правил звёзд. |
| **Т9** | Коды занятий хранятся и проверяются **на сервере игры**; из клиентского конфига они удаляются. Каждый код срабатывает один раз на ребёнка (уникальный ключ). Награды кодов — только монеты/предметы, звёзд не дают. CRM не затрагивается. |
| **Т10** | Механика сундука сохраняется: начисления сверки → сундук; открытие сундука → баланс. Отзыв (`reversal`) списывается сначала из неоткрытого сундука, затем с баланса (с правилом «долга» из раздела 5). |

Открытых вопросов по правилам звёзд нет.
